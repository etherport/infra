`docs/architecture/network.md`, `docs/architecture/overview.md`, and the
`unifi-talk.md` runbook against the live UDM Pro Max state.

**Live snapshot:** `/tmp/unifi-state/` (generated 2026-05-23 via
`scripts/unifi/dump-state.sh`). Auth: tf-admin via 1Password.

**Controller versions probed:** UniFi Network app 9.4.x running on UniFi
OS 5.1.12 ("UDMPROMAX"). All UniFi switches at 7.5.2; APs mixed 6.7.51 /
6.9.1 / 8.6.10. ETPRO IDS/IPS signatures = 72,115 rules, last updated
2026-05-22 04:23 UTC.

**Scope:** UDM (Windroute) + 10 UniFi switches + 7 APs. L3 switch
behaviour observed via the controller API only — no SSH was used.

**What this doc is NOT:** a config change. Nothing was modified on the
UDM during this audit. Recommendations at the bottom are for review and

### 1.2 Zone assignments (the critical drift)

`firewall-zones.md:118-128` defines **six** zones: Trusted, Infrastructure,
IoT, Security, Guest, Legacy. The doc commits to a network-to-zone
mapping where Servers/Clients/Management are "Trusted", vSAN/Unifi/4040
are "Infrastructure", IoT/Security are isolated zones.

Live state (from `zone-matrix.json` + `networks.json.firewall_zone_id`):

| Zone (live) | Zone key | Member networks | Doc says it should be |
|---|---|---|---|
| **Internal** | `internal` | Default, Management/200, Servers/201, Clients/202, **Security/205**, **vSAN/209**, **Unifi/212**, **InterVLAN/4040**, **Ceph/210** | "Trusted" (200/201/202) + "Infrastructure" (209/212/4040) + "Security" (205) — three separate zones in the doc |
| **External** | `external` | WAN1, WAN2, LTE | matches doc semantics |
| **Gateway** | `gateway` | (synthetic — UDM-self) | matches |
| **VPN** | `vpn` | WireGuard WAN1 (UDM-side remote-user-vpn pool) | not in doc |
| **Hotspot** | `hotspot` | Guest/206 | doc calls this "Guest" zone |
| **DMZ** | `dmz` | (none) | not in doc |
| **IoT** | (custom) | IoT/204 | matches "IoT" zone |

**Conclusion — major drift:**

1. Only **one** custom zone exists: `IoT`. The doc describes
   `Trusted`, `Infrastructure`, `Security`, `Guest` as custom zones — none
   of those exist on the UDM. **Doc is aspirational**, not descriptive.
2. **vSAN, Unifi (212), Inter-VLAN (4040), and Security (205) are all in
   `Internal`** alongside the trusted networks. That means the entire
   "Infrastructure Zone Rules" table at `firewall-zones.md:226-231`
   (Unifi-Adoption, Unifi-STUN, vSAN-to-vSAN) is **not enforced** as
   zone-policy — all those flows are silently allowed by the default
   "Internal → Internal: Allow All" zone rule.
3. **Guest is in `Hotspot`** (UniFi's built-in zone), not a custom
   "Guest" zone. This is actually fine — Hotspot exists for exactly this
   purpose — but the doc should say Hotspot.
4. **VPN zone** binds the WireGuard remote-user-vpn pool. The doc
   doesn't model this at all (and prior 2026-05-17 audit also flagged it).

**Decision needed: which side is wrong?**

The doc describes a stricter zone model; the live UDM is more permissive.
Two options:

- **(A) Adopt the doc's design** — create custom zones `Infrastructure`,
  `Security`, `Trusted` and move the relevant networks. Requires
  re-creating the explicit allow rules currently implied by the wide-open
  Internal-to-Internal default. Higher security posture; non-trivial
  migration; risk of breaking SSH-to-PVE / kubectl-from-laptop flows
  during cutover.
- **(B) Update the doc to describe live state** — collapse the
  zone-design section into "everything sensitive lives in Internal; only
  IoT and Guest are segregated." Lower-effort; honest. Loses the
  intent of segregating Security cams + storage networks.

This audit recommends a hybrid: keep the doc's intent as a future-state
design, but mark §"Zone Definitions" / §"Default Policies" / §"Detailed
Zone Policies" as **target architecture not yet implemented**, and add a
"Current state" subsection that mirrors the live IoT-only zone setup.
Then file an issue to migrate networks into custom zones one at a time
(start with Unifi → Infrastructure since Unifi devices only talk to the
controller + STUN; lowest blast radius).

### 1.3 Inter-VLAN allow/deny matrix

`firewall-zones.md:134-141` claims the following default zone-to-zone
matrix:

```
Trusted -> Trusted/Infra/IoT/Security: Allow ; -> Guest: Deny
Infra   -> Trusted/Infra: Allow ; -> IoT/Sec/Guest/Internet: Deny
IoT     -> IoT/Internet: Allow ; -> others: Deny
Security -> Security: Allow ; -> others: Deny
Guest   -> Internet: Allow ; -> others: Deny
Legacy  -> all: Deny
```

Live state (extracted from `firewall-policies.json`, decoded via
`zone-matrix.json`):

| Source → Dest | Live default | Doc says | Match? |
|---|---|---|---|
| Internal → Internal | **Allow All Traffic** | Trusted → Trusted: Allow | ✓ matches |
| Internal → External | **Allow All Traffic** | Trusted → Internet: Allow | ✓ |
| Internal → IoT | **Block All Traffic** | Trusted → IoT: Allow | **DRIFT** (live is stricter) |
| Internal → Gateway | Allow All | (not in doc) | ✓ |
| Internal → VPN | Allow All | (not in doc) | ✓ |
| Internal → Hotspot | Allow All | Trusted → Guest: Deny | **DRIFT** (live is laxer) |
| Internal → DMZ | Allow All | n/a | n/a |
| IoT → Internal | **Block All Traffic** + 1 allow rule ("Allow IoT to DNS") | IoT → Trusted: Deny by default + allow to DNS-Servers:53 | ✓ matches design intent (the only fully-correct policy pair) |
| IoT → External | Allow All | IoT → Internet: Allow | ✓ |
| IoT → Gateway | Allow Return Traffic | (not explicit) | ✓ |
| External → Internal | Block (with 6 named exceptions: Twilio-SIP, Twilio-Media, Wireguard, etc.) | n/a (WAN inbound) | ✓ |
| Hotspot (Guest) → Internal | Block All + Allow Public DNS + post-auth restrictions | Guest → all internal: Deny | ✓ |
| Hotspot (Guest) → External | Allow All (after auth) | Guest → Internet: Allow | ✓ |
| VPN → Internal | Allow All | n/a (doc doesn't model VPN zone) | (open — VPN clients have full LAN reach) |

**Net for §1.3:**

- The IoT zone is **correctly** isolated (with the documented DNS allow rule).
- Internal-to-IoT is **stricter than documented** (live blocks it; doc
  says "Trusted → IoT: Allow"). Practically this means a server on
  10.10.201.x cannot initiate to a Hue bridge on 10.10.204.51 unless a
  specific allow exists. (It doesn't — checked.) Hue control from
  Home Assistant would need to come over Internal-zone return traffic
  or via a dedicated allow.
- Internal-to-Hotspot (Guest) is **laxer than documented** — anything in
  Internal can reach 10.10.206.0/24. Low practical risk (guest devices
  are ephemeral), but the doc claims "Trusted → Guest: Deny" and that
  is not enforced.
- The "Block Invalid Traffic" / "Block All Traffic" / "Allow Return
  Traffic" boilerplate that fills 90+ of the 114 policies is UniFi's
  predefined ruleset (the `predefined: true` flag distinguishes them
  from the 4 user-authored policies — see §1.7).

### 1.10 Summary of Part 1 drift

**Match:** VLAN inventory (10 active), DHCP scopes (10/10), MetalLB IP plan, 3 of 4 port-forwards, predefined zone boilerplate, port-profile names, WAN failover ordering, IDS/IPS enabled posture.

**Doc-side wrong (architectural docs lag reality):**
- "VLAN 1 / Default" labelling (network is untagged)
- VPN zone (WireGuard WAN1) entirely undocumented
- LTE WAN still present in live state, no mention in docs
- VLAN 210 (Ceph) DHCP options and zone assignment

**UDM-side wrong (architectural docs describe target state):**
- 5 custom zones described, only 1 (`IoT`) exists
- Network Isolation enabled on Security/205 (doc says disable)
- Security/205 DHCP DNS cleared (doc implies it should serve .5/.6)
- `Wireguard Travel` port-forward disabled but not deleted
- Site-wide auto-upgrade (`mgmt.auto_upgrade: true`) contradicts the

  scheduler.
- Firmware update channel for the UDM is **`beta`**, not `release`.
  This is in `super_fwupdate.firmware_channel` (independent of the
  "auto-upgrade" toggle). Almost certainly unintentional.

**Unverifiable from API:**
- L3-switch interface-to-VLAN bindings (which VLAN it routes vs. UDM)
- L3-switch ACLs (Deny-Clients-to-vSAN, etc.)

### 2.3 Zone groups (firewall organisation)

UniFi v10 introduced "zone groups" — a way to apply a single policy to
multiple zones. **Not present** on this controller (the API path
`/proxy/network/v2/api/site/default/firewall/zone-groups` returned 404,
and there's no `zone_group_id` field on any policy).

**Recommendation:** **skip** until at least 3-4 custom zones exist. The
current single-custom-zone (`IoT`) topology has no use for grouping.

### 2.4 eBGP peering (overlap with M18)

Tracked separately in `outstanding-work.md:213` (M18). Briefly:

- UDM Pro Max supports eBGP under Network → Settings → Routing → BGP.
- Not configured today (no BGP config visible in `routing.json` or via
  `/proxy/network/v2/api/site/default/routing/bgp` — 404).
- Goal: switch MetalLB from L2Advertisement to BGP, eliminate ARP
  trickery, get per-pod ECMP.

**Recommendation:** **defer**, as M18 already says. Open BGP risk is
that a bad BGPPeer/BGPAdvertisement can blackhole the VIP — MetalLB L2
mode is robust enough today. Re-evaluate after switching the K8s nodes
to a dedicated routing VRF if/when that happens.

### 2.5 Hostname-based VPN client routing

### 3.4 DNS filtering (UDM-side vs. Technitium)

**Current:** Technitium is the authoritative LAN resolver (10.10.201.5 /
.6 via MetalLB + DNS-fallback VM). Per-zone `dhcpd_dns_1/2` points
everything LAN-side at Technitium. UDM's DNS Shield (per-VLAN
content filtering) is **not enabled** on any network (all 15
`dns_filters[].filter: "none"`).

**Trade-offs:**
- Single-source filtering at Technitium is operationally simpler — one
  blocklist, one query log, one UI.
- UDM's filter is a second layer that catches devices that bypass
  Technitium (e.g., a Chromecast that hardcodes 8.8.8.8). It's also
  the only resolver that sees DoH/DoT bypass attempts (UniFi's filter
  is at the firewall layer, not a recursive resolver).

**Recommendation:** **enable UDM-side filtering as a second layer** for
high-risk VLANs only:
- IoT (204) — `filter: "work"` or `"malicious"` blocks ads + malware
- Guest (206) — `filter: "adult"` + `"malicious"`
- Default (199) — `filter: "malicious"` (catch anything that lands here
  by mistake)
- Leave Servers/Clients/Management/vSAN/Unifi/Ceph at `none` — Technitium handles them.

Per-VLAN flag is `dns_filters[<network>].filter = "none|family|adult|work|malicious"`.
